## v2.19.5：接球→最高点手部动作链重做

### v2.19.4 到底错在哪（四个叠加的 root cause）

1. **持球段把手掌钉在“球员局部绝对朝向”上。** `blendHandActorQuat(hand, READY_*_ACTOR_QUAT, …)` 在 lift<0.68 时给手腕一个与肩肘无关的固定目标，再反解成 parent-local。肩从 -0.35 转到 -1.9rad 的同时，手腕被迫等量反转 —— 手掌不跟着大臂走，就是“手全乱”。
2. **辅助手腕位被世界坐标 IK 拽离前臂。** 用 `ballGrip` 世界位置 + 偏移 `worldToLocal` 反解写 `guideHand.position`，但辅助手肩肘仍是公式驱动、没有 IK 链，腕点因此脱离前臂末端。而 `ballGrip` 已挂在投篮手 `handRoot` 下，投篮手一乱，辅助手跟着乱，两个错误相乘。
3. **ready→蓄力有一帧硬跳。** 只有 `G.canShoot&&!G.charging` 分支把大臂 mix 到 -1.88（权重常量 0.5）；按下的瞬间该分支消失，大臂一帧掉约 44°、肘约 25°。
4. **球已硬挂在手上，却还让旧肩肘曲线主导抬球。** 实测旧曲线中段会把球心甩到体前 0.9m 再收回来，球心还会中途下沉 18 帧。

### 现在的结构（改动只在 `src/rendering/motion.js`）

- 整段动作只有 **三个同族关键帧 + 一个相位 + 一种坐标空间**：`SHOT_CATCH_POSE`（迎球）→ `SHOT_READY_POSE`（胸前持球）→ `SHOT_SET_POSE`（T台最高点，常量原封不动）。
- **握球方式从接到球那一刻就定死**：`SHOT_READY_POSE.*.handQuat` 与 `SHOT_CATCH_POSE` 的腕姿直接引用 `SHOT_SET_POSE.*.handQuat`，手指曲度同理。抬球段只有肩和肘在动，手腕相对前臂一格都不转。
- 持球帧的肩肘四元数是**由最高点反解出来的**：把 T台姿势在躯干空间绕 X 放下 91°/开肘 21°，使球心落到体前 `(-.13,1.20,.52)`、辅助手掌心贴球另一侧。
- 迎球帧按用户要求单独反解：大臂只前摆 5°（基本垂在身侧）、内旋 26° 让双手汇拢，小臂**平行地面**前伸，手腕掌屈 72° 把掌心转向来球。结果肘 `(±.285,1.04,.03)`、腕与肘等高（高差 7mm）、双掌 `(±.149,1.10,.30)` 间距 0.30m 正好夹住球。迎球掌面与持球握法差约 130°，由 `CATCH_SETTLE_SECONDS=.28` 的缓冲转回来（约 11°/帧），这一段就是"接住球后调整握法"。
- 抬球段 `k=ease01(lift)`，同一个 k 同时插值肩点、骨长、肩/肘/腕四元数与手指；**k=1 时每一项逐字等于 `SHOT_SET_POSE`**，前段怎么调都动不到最高点。
- 腕部**只写 parent-local**。世界方向约束只保留给出手后的 follow-through（`applyShootingHandWorldFollow`）。
- **压腕与伸肘分成两段相位**（用户第二轮反馈：出手瞬间球会先掉一下）。`ballGrip` 在掌心前方 19cm，压腕会把它从掌上翻到掌下；原来两者共用同一条 `extend` 曲线，球在 `BALL_RELEASE_AT=.092` 脱手时压腕已完成 96%，球心比最高点还低 18.5cm，看着就不是"从托着球的手掌送出去"。现在 `SHOT_WRIST_SNAP_DELAY=.092`（必须等于 `BALL_RELEASE_AT`，check.js 有断言）之前只伸肩肘，球一路升到脱手；球走了手腕才翻。回放/过场/对手的 state 没有 `age`，沿用旧的 extend 相位（对手在最高点就 `oppFireBall()`，本来就没有这个问题）。
- 下蹲蓄力的手臂微沉改用 `addParentXRot(node, -k系数*dip*(1-k))`，带 `(1-k)` 因子保证最高点归零。
- 已删除：`blendHandActorQuat` / `applyActorLocalQuat` / `captureActorLocalQuat` / `READY_*_ACTOR_QUAT` / 辅助手世界位置 IK / `SHOT_SET_BLEND_START`。

### 不要再回头做的事

- 不要在持球段用球员局部/世界绝对朝向钉手腕（`READY_*_ACTOR_QUAT` 那一套）。

## 传球节奏（v2.19.5 第三轮）

用户反馈"传球太快，投篮还没收回手就急匆匆去接球"。拆出三个原因：

1. Rack Rush 传球飞行是 `.22–.32` 秒，5 米传球 = **20 m/s**（其他模式同距离 9.5 m/s），方块画风下就是一道残影。
2. 出手到开始传球的间隔 `delay=(feed-expectedCharge-.27)*1000`，第 4 关起就是 60ms 下限，而出手跟随要 725ms，必然重叠。
3. `updPoseV2` 里接球与跟随是**二选一**，传球一开始 `poseCatchHands` 就从 `poseGuy` 的静止姿势起步，跟随姿势被整个丢掉 —— 这才是"没来得及收回手"的直接原因。

改法：
- 新增 `PASS_FLIGHT_RUSH={base:.26,perMeter:.03,min:.36,max:.5,budget:.43}` 与 `PASS_FLIGHT_NORMAL`，`passFlightSeconds()` 统一出口。5 米传球降到 **12.2 m/s**。
- `shots.js` 的供球间隔改用 `PASS_FLIGHT_RUSH.budget`（原来硬编码 `.27`），check.js 断言它跟着 min/max 中值走，改飞行时长不会连带改掉整关节奏。
- `updPoseV2` 改成叠加：`if(follow.active)applyFollowThroughPose(...)` 之后再 `poseCatchHands(...)`。
- 同时修掉 `poseCatchHands` 里 `hand.quaternion.set(0,0,0,1)` 的无条件重置（改为 `position.lerp` + `blendNodeQuat` 从当前姿势 slerp）。

实测最坏情况（出手 60ms 就传球、跟随与迎球完全重叠）：**105.7 → 27.6°/帧**；而完全不重叠的基线本身就是 30°/帧（压腕自身速度），所以叠加已不引入任何额外跳变。

- 不要把 `node scripts/check.js` 通过当作视觉验收。

## 绝杀模式演员修复（v2.19.5 第四轮）

用户反馈"投进后其他球员抬头反应时头离开身体，运球和走路也不对"。三个独立 bug：

1. **头飞出身体**：`headRoot` 的原点在球员局部 `y≈0.203`（脚踝高度），头网格却挂在它局部 `y=1.62`（`VOXEL_HEAD_PIVOT_Y=1.45`、`SCALE=.86` 推出来的）。直接写 `headRoot.rotation` 会让头沿 **1.39m 半径公转** —— 实测抬头 `.58rad` 头就漂 **0.797m**。`headRoot.rotation` 全项目只有 squad.js 在用，所以只有绝杀模式暴露。修法：新增 `pivotHead()`，旋转后按 `position = P + R·(p0-P)` 重算，把旋转中心搬回脖子。实测漂移 **0.829 → 0.117m**（剩下的是绕脖子转头的正常位移），`bakeActorSegments` 烘焙前后一致。
2. **原地踏步**：`poseRunner` 的 `swing=0.28+run*0.72`，站着不动也摆 0.28rad(16°)。改成 `0.06+run*0.80`，站立 hipX 实测 0.005。
3. **速度被分离污染**：`actor.speed` 用 `p.distanceTo(actor.pos)` 差分，而 `actor.pos` 上一帧被 `separate()` 推挤过，把避让位移算成了跑动 —— 实测冒到 **13.4 m/s**（博尔特百米约 12）。改成纯路径差分 `samplePath(t)` vs `samplePath(t-dt)`，峰值回到 **3.26 m/s**。
4. **球僵在胸前**：持球核心的球固定挂在 `guy.g` 的 `(0,1.12,0.32)`，人在跑球不动。新增 `poseDribble()`，球在体侧 `0.23–0.86m` 之间弹，运球手跟着起落压腕。

5. **全场跟着球在地上点头**：`updatePostShot` 一直收到球的实时位置，球砸框落地弹跳时十个人跟着上下看。新增 `gazeTarget()`：只在球飞向篮筐这一段用眼睛跟，一旦 `made` / `rimSoundPlayed` / `bounces>0` / 球掉到 `HOOP.y` 以下就返回 null，`poseWatcher` 平滑把目光收回篮筐。实测点头反转 **5 次 → 0 次**，末半秒残余抖动 `0.0297 → 0.0001 rad`，最终视线从 +10.5°（低头看地）变成 −10.7°（抬头看筐）。

8. **移动太慢、没有变向换手**：ally0 原路径 7.93m/4.6s = **1.72 m/s**（快走都不如），其他人 0.25–0.72 m/s（基本杵着）。重写编排：核心两次 crossover 突破（6 个路点，11.05m / **2.4 m/s 平均 / 4.95 峰值**），贴防 foe1 跟着变向且每个路点与 ally0 保持约 1.05m（> `MIN_GAP` 0.98，不会被 `separate()` 反复推开），无球队友全部加了切入/外弹。`poseDribble` 按横向位移自动换手（实测两次变向触发 4 次换手），并修掉原来"球固定在 +X、却用 -X 侧的 arms[0] 去拍"的手球异侧 bug。**盯你的 foe0 路径刻意未动** —— 它的路点是为避开两条视线精心调过的。

## 绝杀模式防守 AI（v2.19.5 第五轮）

用户反馈"防守是硬关联、两个人同频同脚步同速度，不像真实攻防""盯我的电脑应该传球后靠近我甚至起跳封盖""冲过来的动作像叉车"。按公开实测数据重做，参数不是拍脑袋定的：

| 参数 | 取值 | 依据 |
|---|---|---|
| `DEF_REACTION` | 0.22s | 横向第一步在进攻方给出线索后 0.2–0.3s 才启动 |
| `DEF_ACCEL` | 7.5 m/s² | 真实横移变向量级；**这是决定性的一个数** |
| `DEF_MARK_SPEED` | 4.0 m/s | 必须低于持球突破 4.95m/s 峰值，crossover 才拉得开 |
| `DEF_CLOSEOUT_SPEED` | 5.6 m/s | 扑防 4–6m 用 0.8–1.0s ⇒ 4–7.5m/s |
| 封盖有效距离 | ≤1.5m | 防守人在投篮肩一个身位内才构成干扰 |

来源：[SimpliFaster 防守动作解构](https://simplifaster.com/articles/deconstructing-preformance-training-basketball-defense/)、[SportsEdTV crossover 分离](https://sportsedtv.com/blog/tim-hardaway-s-signature-move-the-masterful-art-of-the-crossover)、[Reynolds steering behaviors](https://www.red3d.com/cwr/steer/gdc99/)。

**关键教训**：第一版把 `DEF_ACCEL` 设成 15 m/s²，防守人 0.3 秒拉满速，0.22s 的感知延迟被瞬间补掉 —— 实测间距恒定 1.05m、攻防速度逐帧相同，跟改之前一模一样。降到 7.5 之后才出现真实博弈：**间距 0.98–1.96m，最大速度差 3.86 m/s**，crossover 处被甩开 1.92m 再满速追回，与"crossover 制造约 5 feet 分离"吻合。check.js 已把 accel ≤9、markSpeed <4.9 写成断言。

实现要点：
- 对位防守（foe1/3/4）改成 `trailAt(mark, t-DEF_REACTION)` 读延迟位置 → `markTarget` 卡在人与筐之间 → `steerTo`（Reynolds arrive）。**战术包夹 foe2 标了 `help:true` 仍走编排路点** —— 那是剧本不是对抗。
- 盯你的 foe0 是状态机：`help`（协防，离你 7m）→ 球一传出 `closeout`（5.6m/s 扑）→ `contest`（贴到 1.15m）→ 持球超 1.05s 起跳封盖，落地有 0.55s 冷却不会连跳。实测：**持球 0.78s 正常出手 contest=0 完全安全；拖到 1.2–1.5s 撞进窗口（峰值 0.94）**。
- 封盖结算在 `sequence.applyContest()`：球的飞行是解析式 `p0+v0·t-4.9t²`、结果由 `outcome` 分支决定，所以**既要削弱 v0 也要改 outcome**，否则球被打飞了还判进。
- 冲刺庆祝不再写死对称双臂（原来 rush/push 两臂都是 `-1.12`/±`.52`，正是"双手交叉在胸前像叉车"）。改成一只手随步频挥舞（相位用 `actor.phase` 错开）、另一只保留 `poseRunner` 的自然摆臂；`hug` 只在真的贴近了才张开双臂。实测 rush 两臂 -1.95/-0.77、crash -1.12/-1.37，且随时间挥动。

## 绝杀模式阵容与封盖修正（v2.19.5 第六轮）

1. **扑防太快没反应时间**：`DEF_CLOSEOUT_SPEED` 5.6→4.6（实测区间下限）、`CONTEST_GAP` 1.05→1.25（不贴脸）、起跳时机 1.05s→1.25s。正常 0.78s 出手时防守人还在 **2.94m** 外（原来 2.15m），contest=0。

## 封盖改成跟随起跳（v2.19.5 第七轮）

**为什么之前"无论如何都不会盖"**：起跳条件写的是 `chargeT >= 1.25s`（持球满 1.25 秒才跳），但实测**玩家 0.59s 起跳、0.78s 出手，起跳到出手只有 0.19s** —— 任何基于持球时间的阈值都永远等不到，封盖形同虚设。

改成**跟随触发**：
- `sequence` 监测 `P.jump>.04`（你起跳）→ 调 `squadApi.triggerContest()`
- 防守人隔 **0.08–0.28s 随机**（视觉反应）才蹬地起跳 —— 这个随机就是"一定概率"的来源
- 干扰值分两层：`near×(0.45+0.55×rise)`。**贴到正面本身就有 0.45 的干扰**（真实比赛里手举在你脸前就够影响手感，不必起跳）；跳起来且时机对才叠到 0.9+
- `rise` 窗口从起跳那一刻算起（0–0.62s、峰值 0.22s），因为**手是在蹬地瞬间就举满的**，不是等身体升到最高点
- 结果分档：`≥.72` 直接封盖（球被打飞 + outcome=miss）；`≥.38` 按 `Math.random()<level` 概率把结果降级（swish→rattle→rattleout→miss），对应"甜区手感被吃掉"

实测分布（每档 40 次）：**接球立刻出手 40/40 完全不受影响**；犹豫 0.3s → 封盖 15 / 干扰 25；犹豫 0.6s 以上 → 封盖 20 / 干扰 20。

check.js 断言：必须有 `triggerContest`、起跳延迟必须是 `.08+random*.20`、**不得再出现 `chargeT>=CONTEST_JUMP_AT` 这类持球秒表阈值**。

### 第八轮：他一直在侧面、不过来压迫

`updateOnBall` 的 closeout 目标算的是「玩家位置 + **防守人当前方位角** × gap」——他从哪边扑来就停在哪边，永远侧身站着。其余防守人(foe1/3/4)用的都是 `markTarget()`（卡在人与筐之间），只有盯你的这个没用上。

改成同样走 `markTarget(playerPos,gap)`，即堵在**你与篮筐的连线上**（你的投篮路线）。实测偏离投篮路线的角度：**50° → 42° → 31° → 2° → 0°**。

同时加持球压迫：`pressure=clamp((chargeT-.9)/1.1,0,1)`，拖越久贴越近（`CONTEST_GAP-.28*pressure`）、手举越高（`poseContestHands`，armX -0.51 → **-2.28**）。你不投他不会跳（真实防守也这样），但绝不会干站着。实测持球 2 秒时：距离 1.15m、正对 0°、压迫拉满、基础干扰 0.45（触发"手感受影响"档）。

check.js 断言：必须用 `markTarget` 落位、**不得再出现保持方位角的写法**、必须有 `poseContestHands` 与 `actor.pressure` 递增压迫。

## 第九轮：时钟 / 出手反应 / 脚步打滑 / 犯规 / 第一人称碎步

1. **出手后比赛钟继续走**。原来 `if(!LS.released)updClock(clock)` 把钟停在出手瞬间；真实最后一攻里球在空中时间照跑。超时判负仍只在未出手时生效。
2. **出手时防守人绝不干看**：`triggerContest(playerPos)` 按距离与概率分流 —— 3m 内 **78% 起跳封盖**、其余**举手贴住**继续干扰（`handsUp`，也计入 `contestLevel` 的 rise，权重 0.45）；3m 外还在扑的路上就不跳（边跑边跳不合理）但手要举起来。实测 60 次：起跳 47 / 只举手 13 / **啥也不干 0**。
3. **脚步打滑（foot sliding）**：`poseRunner` 的 `phase` 原来按 `dt*(3.4+run*7.2)` 推进 —— 腿的摆动和实际位移各走各的，走一步的时间里身体平移了别的距离，脚就在地上滑。改成**位移驱动**：`phase += (speed*dt/stride)*π`，即"每移动一个步长 = 半个摆动周期"，步长随速度 0.5→1.1m。实测每半周期实际位移 **0.83–1.21m**（恒等于步长），站住不动时腿部残余 **0.0019 rad**。呼吸摆动改用独立的 `idleT`，不再蹭 phase。
4. **投篮犯规**：贴防 `level≥.5` 时 9% 概率吹犯规 —— 球进算 **3+1**，没进给 **三次罚球**，按 76% 罚球命中自动结算（绝杀模式 7 秒定生死，插一段罚球交互会毁掉节奏）。`shotSucceeded()` 把罚中的分算进胜负：你落后 1 分，所以这一攻要拿 ≥2 分才算赢。
5. **第一人称等球时的碎步**：`LS.spot` 记基准点，左右碎步 ±0.18m、前后游走 ±0.10m、镜头脚步起伏 ±1.5cm（频率是碎步的两倍）。传球一开始 `settle` 就把幅度收回 0，**出手时脚下必须是稳的**，不能让人觉得瞄准点在飘。

check.js 断言（均做过变异测试）：步频必须是 `(speed*dt/stride)*Math.PI` 且**不得退回时间驱动**、出手后不得再出现 `if(!LS.released)updClock`、必须有 `CONTEST_JUMP_CHANCE`/`handsUp`、必须有 `FOUL_CHANCE`/`andOne`、必须有 `LS.footT`/`LS.spot`。

## 第十轮：庆祝手势安全 + 个体差异（重要）

用户指出庆祝里出现了**单臂斜前上方举起**的姿势——这个姿势有明确的历史含义，绝不能出现在任何庆祝动作里。核查确认两处命中：

| 动作 | rotation.x | 仰角 | 前伸 | 肘 | 判定 |
|---|---|---|---|---|---|
| `raise` 主手 | -1.85 | **16°** | 0.96 | -0.12(直) | ⚠️ 命中 |
| `rush` 挥舞最高点 | -1.96 | **22°** | 0.93 | -0.04(直) | ⚠️ 命中 |

**判据**：手臂方向 `(0,-cos x,-sin x)`，前伸量 >0.5、仰角在 -12°～55° 之间、且肘接近伸直（|rotation.x|<0.35）。

修法（三层）：
1. **举手一律接近垂直**：`style.lift = -2.72 - random*0.30`（仰角 61°–90°），左右挥动改用 `rotation.z` 的 ±22°–37°，符合用户要求的"接近垂直举起 + 左右 30 度挥动"。
2. **`point` 改成握拳下拉（fist pump）**：手臂留在体侧、肘大幅弯曲（-1.78），从几何上就进不了敏感区间。
3. **`guardArms()` 运行时兜底**：每帧姿势写完后扫两条手臂，命中判据就把肘压到 -0.68。挂在编排与反应两条路径的收尾，即使以后有人改坏参数也兜得住。

**个体差异**：每个 actor 建立时生成 `style{amp,rate,lift,swing,hand,both,bias}` —— 幅度 0.78–1.23、频率 0.82–1.24、举手高度、惯用手左右、举单手还是双手、个体倾斜偏好全部随机。实测 `raise` 时 9 个人举手角度 **9/9 各不相同**，惯用手左右混合、单双手混合。

**全量扫描**：14 种反应 × 9 人 × 2 臂 × 150 帧 = **37800 帧，敏感姿势命中 0**。

check.js 断言（变异测试通过）：`guardArms` 必须存在且挂在两条路径、禁止出现 `-1.85`/`-1.34`/`-1.52-.44` 这三个已知的斜前举硬编码、`lift` 必须在接近垂直区间、`style` 的七个个体参数一个都不能少。

## 第十一轮：手臂自然度 / 穿模 / 反应连贯性 / 抢篮板

1. **举手绷直**：肘只弯 11°–20°，整条手臂像根棍子。改成 **33°–49°**（`-.58-.26*|wave|`），小臂有自然倾斜。
2. **挥手穿头**：实测掌心到头心最近 **0.118m**（头半径 0.16，手直接插进去）。两步修：挥动中心外偏 `ARM_OUT=.48`；再加 `swingZ()` 把**向身体中线的内摆砍到 45%**（外摆不限）——手臂朝上时内摆才是扫进头顶的元凶。全部 14 个动作扫完，最近 **0.346m**，安全。
3. **反应等球弹完才开始**：原来只有 `made` 时即时反应，打铁要等球从 `balls` 里被移除——球在地上弹三下的几秒里全场僵着。新增 `ballSettled()`（进网/触框/开始弹跳/掉到篮筐高度以下，与视线收回同一套判据），结果一定下来就立刻反应；`outcome` 直接预判进否（`MAKE_OUTCOMES`）。球被移除的那条分支降级成兜底。

check.js 断言（变异测试通过）：必须有 `swingZ`/`ARM_OUT`、庆祝肘部不得退回 `-.1x/-.2x/-.3x` 的绷直值、必须有 `ballSettled` 且用它触发反应、不得把 `!activeBall` 当主触发条件、必须有 `boarders` 与 `poseTrailIn`。

## 第十二轮：刚出手就庆祝 / 抢篮板 / 犯规率 / 倒计时音

1. **刚出手就有人冲过来庆祝（我上一轮引入的 bug）**：`ballSettled()` 里用了 `position.y<=HOOP.y` 当"结果已定"的判据，但**出手点才 2.12m、篮筐 3.05m**——球一离手就满足条件。逐帧验证：t=0 旧判据即为真，新判据要到 t=1.05 抛物线飞完才为真。改用 `ball.phase!=="fly"`，并在 check.js 里**反向禁止** `position.y<=HOOP.y`。
2. **庆祝只保留两个启动点**（按用户要求）：① 球真的进框 → 延迟 `CELEBRATE_DELAY=.5s` 开始庆祝；② 没进且**时间走完** → 我方懊恼、对方庆祝。球没进但时间还有，那是抢篮板的混战，谁都不该庆祝。
3. **打铁后没人抢板**：新增 `startRebound()` + `poseRebound()` —— 离球最近的**三个人**冲向落点（4.4m/s），进入 1.5m 且球在 0.9–3.4m 高度就**起跳争抢**。实测 3 人（ally3/foe2/foe4）从 1.86–2.66m 冲到 0–0.01m，起跳抬升 0.48m。
4. **犯规率**：`FOUL_CHANCE` .09 → **.33**（被干扰的出手约三次一次吹犯规，触发三罚或 3+1）。
5. **倒计时音**：原来只在 `clock<=3 && !released && phase==="shoot"` 才响。改成**最后 5 秒**每秒一响，且出手后时钟还在走也继续响到 0，归零补一声 `sBuzz()`。

check.js 断言：禁止用篮筐高度判定结果、必须有 `CELEBRATE_DELAY` 与 `clock<=0` 两条庆祝路径、必须有 `startRebound`/`poseRebound`/`reboundJump`、必须有 `clock<=5` 的倒计时。

## 第十三轮：第一/第三人称同步 + 编排逻辑按编号重做

**第三人称看不到自己在动**：碎步与视线朝向写在 `updateLastShotCam()` 里，而那个函数 `if(CAM.mode!==0)return false` —— 切到第三人称就整个不跑；`P.face` 更是只在 `beginLastShot` 设过一次（朝篮筐）。抽出 `updateBodyState(dt)` 每帧执行、与镜头模式无关，`P.face=LS.lookYaw` 让模型朝向跟着实际视线。**教训：身体状态绝不能写在相机函数里。**

按用户逐条编号反馈改的：

| 编号 | 改动 |
|---|---|
| **D1** | 进球庆祝延迟 0.5s → **0.2s** |
| **D3** | 终场反应延迟 **0.2s**；且**球还在空中时不判负** —— 出手在结束前、球进了就算，等球落定交给 D1/D2 响应 |

## 第十四轮：绝杀模式没有体感 + 罚球改成自己投

**体感一直不出现**：`restoreVisionControlPreference()` 的守卫写死了 `G.state!=="diff"` —— 只有难度选择界面才会自动拉起摄像头。而绝杀时刻是从主菜单直接进 `G.state="lastshot"` 的，**整个模式永远等不到体感启动**。改成 `VISION_AUTO_STATES={diff:true,lastshot:true}` 的白名单。实测：偏好设为 vision 后 `diff`/`lastshot` 都会自动启动，`menu`/`round` 仍不启动（正确）。

**罚球改成玩家自己投**（原来是 76% 概率自动算掉——这是这一攻最关键的几下，不该用骰子解决）：
- `applyContest` 判犯规时只记账 `LS.foul={andOne,shots,made,taken}`，不再结算
- 这一球落定后进入 `phase="freethrow"`：你站上罚球线（篮筐前 4.6m）正对篮筐，**比赛钟停表**（真实规则），`lineUpForFreeThrow()` 把两队沿禁区两侧列队且不挡投篮线
- 每罚用完全一样的蓄力/出手机制（`G.seq` 换成 `val:1` 的罚球），球落定记账，隔 0.6s 进下一罚
- 罚完 `finishFreeThrows()` 结算：3+1 命中即赢；三罚至少中 2 个才赢（你落后 1 分）

check.js 断言（变异测试通过）：`VISION_AUTO_STATES` 必须含 `lastshot` 且不得退回硬编码 `G.state!=="diff"`；必须有 `beginFreeThrows`/`nextFreeThrow`/`updateFreeThrows`/`freethrow` 阶段与 `lineUpForFreeThrow`，且**不得出现按概率批量结算罚球的循环**。

## 第十五轮：罚球没有后续 + 站位按规则重排

1. **罚完最后一球卡死**：`updateFreeThrows` 的第二个分支带了 `f.taken<f.shots` 条件——最后一罚落定后 `f.taken===f.shots`，两个分支都不成立，**什么都不做**，`finishFreeThrows()` 永远不会被调用，整个模式停在罚球阶段。3+1 和三罚都受影响。改成先判 `ftWait>=.6` 再分流：还有罚球就 `nextFreeThrow()`，罚完就 `finishFreeThrows()`。
2. **罚球站位按 NBA 规则重排**：禁区两侧的站位格从底线往罚球线数依次是 **防守 / 进攻 / 防守**。实际占位 **3 名防守 + 2 名进攻穿插**，其余 4 人一律退到三分线外。
   坐标：篮筐 z=-8、底线 z=-9.2、禁区宽 4.9m（x=±2.45）、三格距底线 2.1/3.0/3.9m、罚球线距篮筐 4.6m。
   实测：第 1 格 foe0/foe1（离筐 2.61m）、第 2 格 ally0/ally1（3.04m）、第 3 格 foe2（3.65m）；其余 4 人离筐 7.0–7.2m；**无人挡住罚球线到篮筐的连线**。

check.js 断言（变异测试通过）：最后一罚必须 fall through 到 `finishFreeThrows`、罚球循环不得在罚完后自锁、`FT_LANE` 必须正好 3 个 `def:true` + 2 个 `def:false`、必须有 `FT_ARC` 清空区。

## 第十六轮：绝杀模式开始界面缺少控制模式选择

上一轮改了 `VISION_AUTO_STATES` 白名单，但体感仍然起不来。真正的原因在别处：

`visionModeMarkup()` **既是"触屏/体感"那两个按钮，也是 `restoreVisionControlPreference()` 的唯一触发点**（自动恢复写在它函数体内）。其他模式的难度界面（`src/ui/setup.js`）会插这段 markup，而绝杀模式的 `openLastShot()` 面板虽然把 `G.state` 设成了 `"diff"`、条件其实满足，却从没插入过 —— 结果**既没有选项、也永远不会自动拉起摄像头**。

修法：在 `openLastShot()` 的面板里加上 `visionModeMarkup()`（放在"开始今日挑战"按钮上方，与其他模式一致）。实测面板内出现 `visionMode` 区块与两个按钮，`G.state="diff"`、自动恢复条件成立。

check.js 断言（变异测试通过）：`src/modes/last-shot/index.js` 必须包含 `visionModeMarkup`。

> 环境限制：预览面板禁用摄像头，体感链路只能验证到"UI 出现 + 自动恢复条件成立"，真实识别需在正常浏览器/真机验收。

## 第十七轮：投篮跟随统一 + 两个回归

1. **选体感跳到三分大赛界面（我上一轮引入的回归）**：`enableVisionControl`/`disableVisionControl` 结尾都是 `if(G.state==="diff")goDiff(G.mode,true)`。绝杀模式的开始面板也把 `G.state` 设成 `"diff"`，于是切换控制模式后被 `goDiff` 踢去通用难度界面。改成 `refreshControlPanel()` 按模式分流：`lastshot` 重渲染 `openLastShot()`，其余走 `goDiff`。
2. **确实存在两套出手跟随**：完整跟随（伸肩肘 + 压腕）`applyShotFollowThroughPose` 只有玩家在用；AI 表演赛（三分大赛的电脑）走的是 `applyHandFollowThroughPose` —— **只压腕、不伸肩肘**，所以球出去了手臂还僵在最高点，就是"出手悬停空中"。改成表演赛出手瞬间 `captureShotPose(g)`，之后用与玩家一致的 `followState` + `applyShotFollowThroughPose`。百分大战对手早已走共享路径（`AIBAShotMotion.applyFollowThroughPose`），现在三条路径统一。
3. **热身时两只空手悬在弧顶**：`hands.visible=false` 只关掉旧手模组，而 v2.18 的第一人称镜像骨架 `fpRig` 是另一个对象；热身把镜头搬到弧顶展示球员时 `CAM.mode` 仍是 0，挂在相机上的 fpRig 就停在半空。新增 `FP_HIDDEN_STATES={pregame,aishow,cinematic,victorycine,menu,diff}` 强制隐藏，不再依赖各处记得改 `hands.visible`。

**又一次踩到同一个坑**：check.js 里有条断言写死了 `applyHandFollowThroughPose(g,ease01((ph-.94)/.09))`，等于把旧实现焊死。已改成锁不变量（必须复用共享跟随 + 禁止退回只压腕的写法）。**断言要锁行为，不要锁实现细节。**

## 第十八轮：跑动姿势归一 + 失手诊断 + 练习引导

1. **跑动姿势提到共享层**：新增 `motion.js::poseRunCycle(o,state,speed,dt,opts)` —— 全项目唯一的跑动实现。`squad.js::poseRunner` 与 `cinematics.js` 的 `run` 分支都改为调用它。AI 表演赛原来是 `Math.sin(show.t*16)` 的**时间驱动**腿部摆动（和 squad 修复前一模一样的脚步打滑），现在统一为位移驱动。`state` 由调用方持有（`phase/idleT/lean`），`opts` 支持 `defensive`（张臂）与 `hs`（身高倍率触地）。
2. **失手诊断**：出手瞬间记录 `LS.diag={err,zone,contest,holdT}`（`err=力度-理想力度`），结算面板按情况给出可执行建议：
   - 甜区内 + contest≥.55 → "出手时机没问题 · 被封盖了，别给他起跳时间"
   - 甜区内 + contest≥.38 → "被干扰影响，早零点几秒出手就是空位"
   - 甜区内 → "手感没问题，差一口气"
   - `err<-2×zone` / `err<0` → "蓄力严重不足/偏少 · 出手太早"，附差多少点
   - `err>2×zone` / `err>0` → "蓄力过头/偏多 · 出手太晚"
   - `timeout` → "接球就投，这一攻只有两秒窗口"
3. **正式挑战用完的去处**：结算面板加 `practiceCta()`，引导到投篮机挑战（练出手节奏）/ 百分大战（练对抗）/ 三分大赛（练稳定性）。

check.js 断言：`poseRunCycle` 必须在 motion.js 且位移驱动、squad 与 cinematics 必须复用它、AI 表演赛不得保留自己的时间驱动腿摆、必须有 `missAdvice`/`practiceCta`/`LS.diag`。

## 第十九轮：蓄力过头被误判成"蓄力不足"

用户反馈"蓄力太久了，结果提示的是蓄力太少"。查到根因在 `shot-physics.js::releasePower()`：过了投篮条顶点还没松手，系统按"晚出手"扣力度（`power -= 10+late*28`），**`err=power-ideal` 用的是扣减之后的值**，符号已经不可信——蓄太久也可能被扣成 `err<0`，看起来像"没蓄够"。

数值验证完全对上用户描述的场景：`hold=1.0s`（刚过顶点 0.14s）时 **rawPower=95（明显超蓄）**，扣减后 `err=-13.1`，旧逻辑判成"蓄力偏少"——方向刚好反了。

修法：`AIBAShotPhysics` 新增 `lastLate()`，暴露扣减前的原始 `late` 信号；`shot-motion.js` 在调用 `releasePower` **之前**捕获它存进 `G.lastReleaseLate`；`LS.diag` 一并记录；`missAdvice` 把 `late` 判断**放在 err 判断之前**，分三档：

| late | 反馈 |
|---|---|
| ≥.6 | 蓄力严重超时 · 出手太晚（快到自动出手临界点了）|
| ≥.25 | 蓄力过了顶点 · 出手偏晚 |
| >.02 | 出手略晚 · 刚过顶点（蓄力其实到位，松手慢了一点）|
| 0（真正欠蓄，如 hold=0.6s）| 正常走 err 分支，判"蓄力不足"不变 |

check.js 断言（三条全部变异测试通过）：`lastLate` 必须存在、必须在 `releasePower` **之前**捕获、`missAdvice` 里 late 分支必须排在 err 分支**之前**。

## 第二十轮：犯规几乎永远不触发

用户反馈"玩了 10 盘一次犯规都没有"。根因不是概率调低了，是**门槛挂错了信号**：犯规判定写的是 `level>=.5 && random()<FOUL_CHANCE`，而 `contestLevel` 在防守人 1.9m 之外**恒为 0**——你果断出手时他还在 2.9~3.3m 外，`level=0`，概率乘 0 恒等于 0。

实测各打法出手瞬间的数据：

| 犹豫 | 最近防守距离 | contestLevel | 旧逻辑能否犯规 |
|---|---|---|---|
| 0s（果断） | 3.27m | **0** | ✗ |
| 0.2s | 1.54m | 0.29 | ✗ |
| 0.4s | 1.18m | 0.81 | ✓ |
| 0.6s | 1.15m | 0.45 | ✗ |
| 1.0s | 1.15m | 0.72 | ✓ |

即使按五种打法均匀分布算，名义 33% 的实际触发率也只有 **13.2%**；而真实玩家多半果断出手（level=0），实际接近 0。

修法：新增 `squad.defenderDistance()`，犯规改用**距离**门槛 `FOUL_RANGE=3.4m`（刚好覆盖果断出手时的 3.27m）。蒙特卡洛 2 万次验证，名义概率现在等于实际触发率：测试值 .5 → **49.9%**，上线值 .33 → **33.4%**。

> **上线前必做**：`sequence.js` 里把 `const FOUL_CHANCE=FOUL_CHANCE_TEST` 改成 `FOUL_CHANCE_LIVE`（.5 → .33）。两个常量都已定义好，只改这一处。

check.js 断言（两条均变异测试通过）：必须有 `defenderDistance`、犯规必须按距离门槛判定、**禁止退回 `level>=.5` 的写法**。

## 第二十一轮：第一人称机位过高

用户反馈"接球看不到手和球""投完防守方过来只看到头发、看不到脸"。两个现象同源：**不举球时相机站在 2.06m**（`EYE 1.78 + fpRise 0.28`），比防守人头顶 1.84m 还高 0.22m。

用真实相机矩阵投影验证（NDC y=-1 是画面下缘）：

| | 旧 FP_RISE=.28 | 新 FP_RISE=.05 |
|---|---|---|
| 相机高（不举球） | 2.06m | 1.75m |
| 对方头部相对角 | −12.2°（俯视头顶） | **−1.4°（平视见脸）** |
| 持球时球 ndcY | −1.04 **出画** | −0.79 ✓ |
| 持球时腕 ndcY | −1.28 **出画** | −0.99 ✓ |

修法两步：
1. `fpRise` 基础值 0.28 → `FP_RISE=0.05`，同时 `FP_BALL_DUCK` 0.46 → 0.23，**保持举球到位的最终高度精确落在 1.60m**（这是已经调好的投篮取景，不能动）。
2. 下压曲线区间从 `rel∈[-0.25,0.20]` 放宽到 `[-0.95,0.14]` —— 原曲线只在球快到眼睛高度才介入，刚接到球（球在腰腹、`rel≈-0.63`）时完全不下压，手被压在画面外。

全阶段验证：刚接球 1.75m / 抬球中段 1.68m / 举球到位 1.60m，球与腕**全部在画面内**。

绝杀模式观看阶段的相机原本写死 `eye.y+0.28`，现已改为共享 `FP_RISE`。

check.js 断言（两条均变异测试通过）：`FP_RISE ≤ .12`、`EYE+FP_RISE-FP_BALL_DUCK` 必须保持 1.60±0.03、下压曲线不得退回只在眼高附近介入的旧区间、绝杀观看相机必须共享 `FP_RISE`。

## 第二十二轮：竖屏水平视野只有 35°

用户"投了几次都看不到手，球从屏幕左侧出去"，并给了三张**竖屏**截图。前一轮我所有验证都用横屏 `aspect=1.78`，漏掉了这个变量。

根因：`camera` 是 `PerspectiveCamera(68,...)`，THREE 的 fov 是**垂直**视角，`resize()` 只改 aspect 不改 fov。竖屏 375×812（aspect 0.46）时垂直 68° 换算出的**水平视角只剩 35°**（横屏是 100°）——贴到面前的防守人糊满半屏，自己的手被挤到画面边缘。

截图佐证：左侧那个深色大头和举起的手臂是**防守人**（贴防 1.15m + 相机后拉 1.1m，在 35° 水平视野里占了近一半画面）；玩家自己的手（浅色）只在 follow-through 时露出画面底部。

修法：`resize()` 加 Hor+ 补偿 —— 锁定基准水平视角（16:9 下的 100°），竖屏反解出需要的垂直 fov，`MAX_VFOV=90` 封顶（再高竖屏透视会明显变形，手游竖屏一般 75–90）。横屏走 `Math.max(BASE_VFOV,...)` 保持原来的 68° 不变。

| 视口 | aspect | 垂直 fov | 水平 FOV |
|---|---|---|---|
| iPhone 竖屏 | 0.46 | 68→**90** | 35°→**50°** |
| 平板竖屏 | 0.75 | 68→90 | 54°→**76°** |
| 横屏 16:9 | 1.78 | **68 不变** | **100 不变** |

真实相机路径投影验证（竖屏、出手瞬间）：腕 NDC x 0.49→**0.33**、球 0.31→**0.21**，都明显回到画面中心区。

> 这是**全局改动**，影响所有模式的竖屏取景（不只绝杀），横屏完全不受影响。

check.js 断言（两条变异测试通过）：必须有 `fovForAspect` 且在 resize 中生效、`MAX_VFOV` 必须落在 80–95、横屏必须保底 `BASE_VFOV`。

## 第二十三轮：接球后身体转回持球人（我引入的回归）

用户："接球前是对的，接球后手和球就不见了，还是在屏幕左侧。"——"接球前对、接球后错"直接指到 `updateLastShotCam`（观看阶段）交棒给 `updPlayCam` 的那一刻。

根因是第十七轮我加 `updateBodyState()` 时留的坑：朝向目标写的是
```js
const target=handler?V3(handler.pos.x,1.5,handler.pos.z):V3(HOOP.x,HOOP.y,HOOP.z);
if(LS.pass){ /* 传球途中 lerp 向篮筐 */ }
```
传球飞行结束后 `LS.pass` 被清空，lerp 分支不再进入，**target 退回持球人位置** → `P.face` 转向左路的核心 → 投篮手被甩出画面左侧。

在真实绝杀流程里复现（手机竖屏 375×812）：

| | 修复前 | 修复后 |
|---|---|---|
| 朝向偏离篮筐 | 转向持球人 | **0.6°** |
| 腕 NDC x | **−1.27 出画** | **+0.16** ✓ |
| 球 NDC x | **−1.50 出画** | **−0.03** ✓ |

修法：加 `inHand=G.canShoot&&!LS.released`，球一到手 target 就锁定篮筐。

**教训**：前两轮我一直用手动摆位的场景验证（`P.pos=RACKS[3]`、`P.face=faceTo(spot,HOOP)`），得出"手在画面内"的结论，但那绕开了 `updateBodyState` 实际写入的 `P.face`。**验证必须跑真实入口**（`beginLastShot` → `updateLastShot` 循环），不能自己重建场景。

check.js 断言（变异测试通过）：必须有 `inHand` 判断，球在手时朝向目标必须是篮筐。

## 关键技术决策

1. 第三人称球员骨骼与 `shot-motion.js` 姿势是唯一动作真源。第一人称只能镜像，不得再维护第二套蓄力/出手曲线。
2. 投篮物理只使用真实球员持球锚点 `pBall`，不得使用相机专用 `handBall`。
3. 新逻辑只能写入 `src/`，禁止向 `index.html` 新增内联游戏逻辑。

## v2.19.2 历史记录：投篮手与辅助手持球关系（已被 v2.19.3 T台骨架替代）

> 以下数值只记录 v2.19.2 的排查过程，不能再作为当前实现依据。v2.19.3 已移除 `BALL_IN_ELBOW`、固定掌面 Euler 和运行时手指反解；v2.19.4 又移除了错误冻结前段动作的 `SHOT_HOLD_POSE`。当前最高点真源是 `SHOT_SET_POSE` 与 handRoot 下的 `ballGrip`，接球/前段蓄力使用恢复后的连续曲线。

这一条当时**不属于绝杀时刻**，改的是 `src/rendering/motion.js` 的共用投篮姿势，三分大赛/百分大战/投篮机的三个机位都会变。

- 问题:上一轮把球心放到掌心上方，投篮手和辅助手都像在球顶端托球，且拇指位于两手外侧。
- 当时统一值:`ballGrip=(.01,-.105,.065)`、`BALL_IN_ELBOW={y:-.105,z:.065}`、无独立锚点时的 `pBall` 回退坐标三处一致;`SHOOT_HAND_PITCH=-PI/2` 让掌心朝上、四指朝脸侧；角色构建把拇指改到两手内侧。
- 辅助手不再用投篮手的球心反解，而是以真实 `ballGrip` 世界位置为目标，从球侧约 `.205` 的位置轻搭，避免悬空或穿球。
- `shotIdeal`、`playerSweetZone` 和 `releaseShot` 的力度结果公式没有改;但 `pBall` 的真实出手原点随球心修正移动,因此飞行距离、弧线和第一/第三人称画面仍需人工验收。
- 接球通过 `G.passCatch` 驱动双臂从两侧/下方抬起，球到手后才进入 `G.canShoot` 的双手准备姿势。
### 第一人称眼线与"看不到自己肩膀"

- **不要再把肩和上臂镜像进第一人称**。第一人称相机在眼睛后方 `0.85`,自己的肩正对镜头;手臂垂着时那截圆角肩块糊在画面底部,看着像"一只没手腕没手指的手"(实测 `shoulderBlend<fpGuideArm` 落在屏幕 30%,93%,而同一条手臂的手掌在 110% 已出画)。`shot-motion.js` 的 `FP_HIDDEN_PARTS` 负责隐藏,并且 `syncArmMirror` 每帧同步可见性时必须尊重这个标记,否则会被真实球员的 `visible` 覆盖回来。
- **举球时第一人称相机要下压**。原本恒定 `e.y+0.28`,实测举球到顶时相机 `2.51` / 球心 `2.34` —— 眼线高过球,变成低头看自己的手。现在按球心相对眼睛的高度平滑下压(`FP_BALL_DUCK`),球在腰间完全不生效,举到顶时相机落到 `2.15`(球下方 `0.19`),仰视球。篮筐屏幕位置不变(仍 50%,51%)。

### 待静音人工验收:第一人称投篮手与篮球的相对位置

当时静态几何目标是掌心离球心约 `.17~.19`、掌面法线点积至少 `.9`;浏览器中的遮挡轮廓、两只手的侧/下方入画和出手后是否自然回腕仍需静音人工确认。

- 不再继续压相机或单独张开手指;相机只负责取景,手球相对位置由共用骨骼和 `ballGrip` 决定。
- 需要人工确认四点:投篮手掌托在球下后侧;辅助手只搭球侧;接球时双手从画面两侧/下方抬起;出手后 `pBall` 从同一挂点离手且命中手感没有明显变化。

### 手指贴球:改成运行时几何反解,不要再硬编码角度

手指原本四根统一 `HAND_FINGER_REST=-.08`,是一排平板,不贴球。当时 `solveFingerWrap()` 每帧按新的 `BALL_IN_ELBOW` 球心几何反解:
指尖 = 指根 + L·(0,-cosθ,-sinθ),要求 `|指尖-球心| = .16+.015`,展开成 `A·cosθ+B·sinθ=k` 解 θ。

- **不要退回硬编码角度**。试过,不行:手一俯仰指根就换位置,同一组角度在不同蓄力相位下指尖会从 `.18` 漂到 `.26`。四根手指长度和指根位置本来就不同,反解会自动给出四个不同角度——自然弧度是算出来的,不是估的。
- 只接受 `[-1.4,0]` 的负解(往球面扣)。方程在手够不到球时仍可能给出正解,那是手指往反方向掰过去够球,很怪,所以够不到就退回自然微屈。
- 实测投篮手指尖 `.175/.178/.178/.187`(目标球面 `.175`),早期与后期蓄力基本不漂。侧向张开 `SHOOT_FINGER_SPLAY` 让四指铺开,指尖间距 `.084 → .100`。
- 压腕跟随 `HAND_FINGER_FOLLOW=[.14,.38,Math.PI/6,.16]` 完全没动,出手后仍由它整体接管(已回归:出手命中正常)。

- 这一轮已补齐投篮手掌朝向和辅助手侧向目标，但双手在不同屏幕比例下的遮挡轮廓仍必须静音人工验收。

## 绝杀时刻 · 当前边界

- **每日一次的闸门目前只在本地**（`localStorage` 键 `aiba.lastshot.v1`）。清缓存、换设备或换浏览器都能再拿一次机会，因此现在这套 streak **不具备做正式榜单的资格**。服务端方案（`daily_attempts` 表 + 开赛发 attempt_id + UNIQUE(player_id, challenge_date)）尚未实现。
- 机会在开赛那一刻消耗，不是等出结果。中途刷新/杀进程再进来会被 `settlePending()` 判为 `abandon`：当天用完且 streak 清零。这是刻意的，避免"刷新重来"变成免费重试；服务端版本要把技术异常和真失败分开处理。
- 首关是致敬版，刻意不使用真实球员姓名、号码、球队配色与 Logo，只复刻情境。加新关卡时必须守住这条。
- 本模式不接 `pauseableState()`：每天一次的正式挑战不允许中途暂停。
- 9 个 5v5 演员在首次进入模式时才创建，并全部 `bakeActorSegments` 烘焙；他们配色固定，不要在烘焙后再调 `dressGuy`（不会生效）。共用的 `passer`/`oppPasser` 在本模式全程隐藏，传球由模式自己实现。
- 出手后由 `squad.startPostShot/updatePostShot/startReaction` 驱动转身追球和反应，反应窗口约 3.6 秒后才进入结算；绝杀路径明确跳过 `startHero`。
